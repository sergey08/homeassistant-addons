# Nod Workspace experimental protocol

Dev.3 keeps offline mode by default. Optional TLS-PSK transport accepts only the configured Nod Server peer. With `command_enabled: true`, it carries the original pinned Nod command supervisor, including stdout/stderr frames, exit status, cancellation and stop confirmation. Caller-supplied supervisor programs and connected CLI credentials are rejected. Task directories are opened without following symlinks. Commands run as UID 1000 without capabilities, host mounts, host Docker or network access; task directories share the same container user as upstream, rather than a separate security principal per thread.

Limits: two active ordinary commands plus one recovery supervisor, one MiB request, 16 MiB output, ten-minute requested command duration, 256 processes per real UID via RLIMIT_NPROC, 128 open descriptors and 128 MiB per created file. RLIMIT_NPROC is shared by the real UID and is not a cgroup limit; these are not aggregate container CPU/RAM limits. CI separately caps its disposable container to 128 PIDs and 2 GiB RAM. The Nod agent launcher remains disconnected in Server dev.13; this release validates transport using synthetic programs only. Further resource/isolation validation is required before enabling agent tasks.

Use an independent random 256-bit hexadecimal key in both apps. On Workspace configure `remote_enabled`, `remote_key` and `server_host`. On Server use `workspace_probe_enabled`, `workspace_key` and `workspace_host`; opt into synthetic upstream checks with `workspace_command_probe_enabled`. No key belongs in chat, logs or arguments. Disable command mode and the diagnostic to return to the fixed preflight. Data persists across restarts.

## Español

La dev.3 mantiene el modo sin red por defecto. El transporte opcional TLS-PSK acepta únicamente al Nod Server configurado. Con `command_enabled: true` transporta el supervisor original de órdenes de Nod fijado por revisión, con salida normal/error, estado final, cancelación y confirmación de parada. Rechaza programas de supervisión aportados por el cliente y credenciales de CLI conectadas. Abre los directorios de tarea sin seguir enlaces simbólicos. Las órdenes usan UID 1000 sin capacidades, montajes del host, Docker del host ni acceso a red; los directorios comparten usuario de contenedor como upstream y no tienen un usuario de seguridad distinto por hilo.

Límites: dos órdenes normales activas más un supervisor de recuperación, petición de un MiB, salida de 16 MiB, duración solicitada de diez minutos, 256 procesos por UID real mediante RLIMIT_NPROC, 128 descriptores y 128 MiB por archivo creado. RLIMIT_NPROC se comparte por UID real y no es un límite cgroup; estos controles no limitan CPU/RAM agregada del contenedor. CI limita además su contenedor desechable a 128 PID y 2 GiB RAM. El launcher del agente sigue desconectado en Server dev.13: esta versión valida el transporte con programas sintéticos. Falta validar recursos y aislamiento antes de habilitar tareas del agente.

Configura una clave hexadecimal aleatoria propia de 256 bits en ambas aplicaciones. En Workspace usa `remote_enabled`, `remote_key` y `server_host`. En Server usa `workspace_probe_enabled`, `workspace_key` y `workspace_host`, y activa la prueba sintética del protocolo con `workspace_command_probe_enabled`. No copies claves al chat, registros ni argumentos. Desactiva el modo de órdenes y el diagnóstico para volver a la prueba fija. Los datos persisten tras reinicios.
